## Section 1: Selenium Framework / POM Model + TestNG/JUnit

> **Evaluate:** Architecture understanding, not just usage. SDETs at this level
> should own frameworks, not just write tests.

### What to Observe

- Do they distinguish between PageFactory vs plain POM?
- Can they explain `@FindBy` lazy initialization?
- Do they understand test parallelism implications?
- Do they mention maintenance challenges, not just setup?

### Cross Questions to Probe Deeper

- "You mentioned POM — show me how your Page class is structured."
- "What happens when the DOM changes? How does your framework handle it?"
- "Have you ever had flaky tests? Root cause?"
- "How do you share WebDriver instances across tests safely?"

---

### Questions

**Q1.** Explain the Page Object Model pattern. Why is it preferred over direct
locator usage in test classes?

> **Observe:** Separation of concerns, reusability, maintenance. Red flag:
> defines POM only as "putting locators in a class."

---

**Q2.** What is the difference between `PageFactory.initElements()` and
instantiating WebElements directly in a constructor?

> **Observe:** Should explain lazy loading — `PageFactory` uses proxy objects;
> elements are resolved only when accessed, not at instantiation.

---

**Q3.** How do you handle dynamic web elements that don't have stable IDs or
class names?

> **Observe:** XPath strategies (sibling, ancestor, contains), CSS attribute
> selectors, custom `data-testid` convention advocacy.

---

**Q4.** [Scenario] Your POM-based suite has 500 tests. A UI redesign changes 30
locators. How do you minimize the blast radius?

> **Observe:** Centralized locator repositories, component-level pages (header,
> footer), locator constants file.

---

**Q5.** Explain `@DataProvider` in TestNG. How is it different from
`@ParameterizedTest` in JUnit 5?

> **Observe:** TestNG `@DataProvider` returns `Object[][]`; JUnit 5 uses
> `@MethodSource` / `@CsvSource`. Candidate should know both if profile
> warrants.

---

**Q6.** How do you configure parallel test execution in TestNG? What
thread-safety issues arise?

> **Observe:** `testng.xml` `parallel="methods|classes|tests"`, `thread-count`.
> Thread-local WebDriver pattern — should know `ThreadLocal<WebDriver>`.

---

**Q7.** What is a `TestNG Listener`? Give a real use case you implemented.

> **Observe:** `ITestListener`, `IRetryAnalyzer`, screenshot on failure. Red
> flag: only knows it exists but hasn't implemented one.

---

**Q8.** [Scenario] Two tests in your TestNG suite are inter-dependent — Test B
needs data created by Test A. How do you handle this?

> **Observe:** `dependsOnMethods`, but more mature answer: avoid dependency, use
> setup/teardown with APIs to create data. Shared state is a smell.

---

**Q9.** Explain `StaleElementReferenceException`. When does it occur and how do
you prevent it?

> **Observe:** DOM re-rendered after element reference captured. Fix: re-query,
> use `ExpectedConditions`, avoid storing elements long-term.

---

**Q10.** How do you implement a retry mechanism for flaky tests in Selenium +
TestNG?

> **Observe:** `IRetryAnalyzer`, `@Test(retryAnalyzer = RetryClass.class)`.
> Should mention this is a band-aid — root cause is more important.

---

**Q11.** What is `WebDriverWait` vs `FluentWait`? When would you prefer
`FluentWait`?

> **Observe:** `FluentWait` allows custom polling intervals and ignored
> exceptions. Used for unpredictable load times. `WebDriverWait` extends
> `FluentWait` with 500ms default polling.

---

**Q12.** [Scenario] Your Selenium grid has 10 nodes. How do you route specific
tests to specific browsers or OS configurations?

> **Observe:** Selenium Grid capabilities, `DesiredCapabilities` /
> `ChromeOptions`, capability matching.

---

**Q13.** Explain the `@Factory` annotation in TestNG.

> **Observe:** Creates multiple instances of a test class with different
> constructor params. Used for data-driven class-level instantiation. Different
> from `@DataProvider` which feeds individual test methods.

---

**Q14.** How do you manage test configuration (URLs, credentials, environments)
in a Selenium framework?

> **Observe:** `.properties` files, `System.getProperty()`, environment
> variables, config frameworks like Owner or Typesafe Config.

---

**Q15.** What design patterns beyond POM have you used in your framework?

> **Observe:** Singleton (WebDriver), Builder (test data), Strategy (different
> wait strategies), Factory (browser factory). Red flag: only knows POM.

---

**Q16.** [Scenario] Your CI pipeline shows tests passing locally but failing on
headless Chrome in Docker. How do you debug?

> **Observe:** Headless rendering differences, missing fonts, viewport size,
> Docker memory limits, `--no-sandbox` flags, video recording in CI.

---

**Q17.** How do you handle file downloads in Selenium tests? What are the
challenges?

> **Observe:** Setting Chrome download prefs, headless restrictions, temp
> directory cleanup, asserting file exists after download.

---

**Q18.** Explain `@BeforeSuite`, `@BeforeClass`, `@BeforeMethod` execution order
and your real usage of each.

> **Observe:** Suite → Class → Method hierarchy. Suite: start WebDriver pool.
> Class: navigate to feature section. Method: login fresh, reset data.

---

**Q19.** [Scenario] You need to run the same test suite against 3 environments
(dev, staging, prod). How do you architect this?

> **Observe:** Environment-specific config, Maven profiles or Gradle tasks, CI
> parameters, environment-aware base URLs and credentials.

---

**Q20.** How do you generate meaningful test reports? Have you integrated Allure
or ExtentReports?

> **Observe:** Allure annotations `@Step`, `@Attachment`, `@Description`.
> Integration with CI to publish HTML. Screenshot/log attachment on failure.

## Section 1B: Live Coding — Write a Playwright Test (Page Object Model)

> **Evaluate:** Hands-on ability to translate a real user flow into a clean,
> deterministic Playwright test **structured with the Page Object Model**. Pair
> this with a shared editor (VS Code Live Share, CoderPad, or screen share).
> Give the candidate 20–25 minutes. Watch how they think about separation of
> concerns, not just what they type.

### Scenario

> "Our app is the todo site at `https://demo.playwright.dev/todomvc`. 
> Write a Playwright test in TypeScript
>
> 1. Navigate to the app.
> 2. Add three todo items: `Buy milk`, `Walk dog`, `Pay rent`.
> 3. Mark `Walk dog` as completed.
> 4. Assert that the active todo count shows `2 items left`.
> 5. Filter by `Completed` and assert only `Walk dog` is visible.
>
> Keep locators and interaction logic in the page object — no raw selectors in
> the spec file. Talk me through your design as you write."

### What to Observe

- **Page Object structure:** locators as `readonly` private fields, actions as
  public async methods, no `expect()` calls inside the page object (assertions
  belong in the spec, or in a thin assertion helper).
- Constructor takes a `Page` and initializes locators once — no re-querying
  inside every method.
- Uses `locator()` / `getByRole` / `getByPlaceholder` / `getByTestId` over
  brittle CSS or XPath.
- Relies on auto-waiting (`expect(...).toBeVisible()`, `.toHaveText()`,
  `.toHaveCount()`) — no `waitForTimeout()`.
- Action methods are named in business terms (`addTodo`, `completeTodo`,
  `filterByCompleted`), not DOM terms (`clickInput`).
- Spec reads like a user story; no leaked implementation details.
- Knows when to expose a locator (for assertions) vs. wrap it in a method.

### Cross Questions While They Code

- "Why does `expect()` live in the spec and not in `TodoPage`?"
- "If the placeholder text changes, how many files need to change?"
- "How would you extend this for a multi-page flow — base page class, fixture,
  or composition?"
- "Would you turn `TodoPage` into a Playwright fixture? What's the trade-off?"
- "How would you reuse `addTodo` for an API-based data setup instead of UI?"

### Reference Solution

**`pages/TodoPage.ts`**

```typescript
import { Page, Locator, expect } from "@playwright/test";

export class TodoPage {
  readonly page: Page;
  readonly newTodoInput: Locator;
  readonly todoItems: Locator;
  readonly todoCount: Locator;
  readonly completedFilter: Locator;

  constructor(page: Page) {
    this.page = page;
    this.newTodoInput = page.getByPlaceholder("What needs to be done?");
    this.todoItems = page.getByTestId("todo-item");
    this.todoCount = page.locator(".todo-count");
    this.completedFilter = page.getByRole("link", { name: "Completed" });
  }

  async goto() {
    await this.page.goto("https://demo.playwright.dev/todomvc");
  }

  async addTodo(text: string) {
    await this.newTodoInput.fill(text);
    await this.newTodoInput.press("Enter");
  }

  async addTodos(items: string[]) {
    for (const item of items) {
      await this.addTodo(item);
    }
  }

  async completeTodo(text: string) {
    await this.todoItems
      .filter({ hasText: text })
      .getByRole("checkbox")
      .check();
  }

  async filterByCompleted() {
    await this.completedFilter.click();
  }
}
```

**`tests/todo.spec.ts`**

```typescript
import { test, expect } from "@playwright/test";
import { TodoPage } from "../pages/TodoPage";

test("user can add, complete, and filter todos", async ({ page }) => {
  const todoPage = new TodoPage(page);

  await test.step("open app and add todos", async () => {
    await todoPage.goto();
    await todoPage.addTodos(["Buy milk", "Walk dog", "Pay rent"]);
    await expect(todoPage.todoItems).toHaveCount(3);
  });

  await test.step("complete one todo", async () => {
    await todoPage.completeTodo("Walk dog");
    await expect(todoPage.todoCount).toHaveText("2 items left");
  });

  await test.step("filter by completed", async () => {
    await todoPage.filterByCompleted();
    await expect(todoPage.todoItems).toHaveCount(1);
    await expect(todoPage.todoItems).toHaveText("Walk dog");
  });
});
```

### Red Flags

- Puts `expect()` assertions inside the page object class.
- Returns locators from every method instead of performing actions.
- Re-creates locators inside each method (no field initialization in the
  constructor).
- Leaks raw selectors (`.todo-count`, `[data-testid=...]`) into the spec.
- Uses `page.waitForTimeout()` to "stabilize" the test.
- Cannot explain the trade-off between a page object class and a Playwright
  fixture.
- Writes the spec top-to-bottom without thinking about reuse or isolation.

## Section 2: Playwright (Core Focus — 40 Questions)

> **Evaluate:** This is the primary tech. Expect deep answers. Junior answers on
> Playwright at 6–10 years is a red flag.

### What to Observe

- Do they own Playwright config end-to-end?
- Do they understand browser contexts vs pages and why it matters?
- Can they explain network interception practically?
- Do they mention retry strategies, soft assertions, and trace viewer?

### Cross Questions

- "Walk me through your `playwright.config.ts` — every option and why."
- "How do you handle auth state sharing across tests?"
- "Have you ever used `page.route()`? For what?"
- "How do you debug a test that only fails in CI?"

---

### Questions

**Q1.** What is the difference between `page`, `context`, and `browser` in
Playwright's object hierarchy?

> **Observe:** Browser → BrowserContext → Page. Context is like an incognito
> profile — isolated cookies/storage. Multiple pages per context, multiple
> contexts per browser. Essential for multi-user scenarios.

---

**Q2.** Why does Playwright not require explicit waits as often as Selenium?
What is auto-waiting?

> **Observe:** Playwright auto-waits for actionability: visible, enabled,
> stable, attached to DOM. `click()`, `fill()`, `check()` all wait internally.
> Not infinite — uses `timeout`.

---

**Q3.** Explain the difference between `locator.click()` and `page.click()`.
Which should you prefer and why?

> **Observe:** `page.click(selector)` is legacy — evaluates selector at call
> time. `locator()` is lazy and re-evaluated on every action. Locators are
> composable and auto-waiting. Always prefer `locator`.

---

**Q4.** What is a `BrowserContext`? Give two real scenarios where you'd use
multiple contexts in one test.

> **Observe:** (1) Multi-user flows — admin + regular user without two browser
> instances. (2) Testing notifications/real-time features from sender → receiver
> context.

---

**Q5.** How does `page.route()` work? Describe a test where you used it to mock
an API response.

> **Observe:** Intercepts network requests matching pattern.
> `route.fulfill({ json: {...} })` returns mock data. Used for: testing error
> states, avoiding external calls, performance test data isolation.

---

**Q6.** Explain `storageState` in Playwright. How does it improve test
performance?

> **Observe:** Saves cookies + localStorage after login. Re-used via
> `context.storageState` / `use.storageState` in config. Avoids login per test.
> Auth setup as global setup fixture.

---

**Q7.** [Scenario] You have 200 tests requiring authentication. Logging in per
test makes the suite 10x slower. Design a solution.

> **Observe:** `globalSetup` to login once, save `storageState.json`. Each test
> loads state via fixture. For multi-role: save N state files. Invalidation
> strategy when token expires.

---

**Q8.** What is the Playwright Trace Viewer? How do you use it in debugging CI
failures?

> **Observe:** `trace: 'on-first-retry'` or `'retain-on-failure'`. Opens zip
> with step-by-step screenshots, network, DOM snapshots.
> `npx playwright show-trace trace.zip`. Essential for CI-only failures.

---

**Q9.** How does Playwright handle iframes? What are the limitations?

> **Observe:** `page.frameLocator('iframe')` chains locators inside frame. Frame
> must be accessible (no cross-origin blocking). `frame.locator()` for
> named/URL-matched frames.

---

**Q10.** Explain `expect(locator).toBeVisible()` vs
`locator.waitFor({ state: 'visible' })`. When would you use each?

> **Observe:** `expect` is assertion with soft-assertion support, built for test
> assertions. `waitFor` is a utility wait — use when waiting before doing an
> action, not asserting.

---

**Q11.** [Scenario] A dropdown uses a custom web component (shadow DOM). Your
`locator('select')` doesn't find it. How do you handle this?

> **Observe:** >
> `page.locator('custom-element').locator('internal:shadow=select')` or pierce
> shadow DOM with `>>`. Playwright supports shadow DOM piercing natively with
> `>>>`.

---

**Q12.** How do you run Playwright tests in parallel? What configuration
controls this?

> **Observe:** `workers` in `playwright.config.ts`. Each worker gets its own
> browser context. Tests within a file run serially by default —
> `test.describe.configure({ mode: 'parallel' })` for parallel within file.
> Shared state = race conditions.

---

**Q13.** What is `test.use()` in Playwright? How does it differ from fixtures?

> **Observe:** `test.use({ viewport, storageState, baseURL })` — overrides
> config options for a `describe` block or file. Fixtures provide
> dependency-injected objects. `test.use` is config-scoping; fixtures are object
> provisioning.

---

**Q14.** Explain Playwright fixtures. Write the skeleton of a custom fixture
that provides a logged-in page.

> **Observe:**

```typescript
const test = base.extend<{ loggedInPage: Page }>({
  loggedInPage: async ({ page }, use) => {
    await page.goto("/login");
    await page.fill("#email", "user@test.com");
    await page.click("button[type=submit]");
    await use(page); // teardown after this
    await page.close();
  },
});
```

Should explain `use()` as the yield point.

---

**Q15.** What are soft assertions in Playwright? When should you use them vs
hard assertions?

> **Observe:** `expect.soft()` — records failure but continues test. Use when
> checking multiple independent fields (form validation). Hard assertions stop
> on first failure. Over-using soft assertions hides cascading bugs.

---

**Q16.** [Scenario] You need to test a file upload flow. The file picker opens a
native OS dialog. How do you handle it?

> **Observe:** `page.setInputFiles()` bypasses OS dialog — directly sets files
> on `<input type="file">`. For drag-drop: `page.dispatchEvent()` with
> DataTransfer. No native dialog workarounds needed.

---

**Q17.** How do you capture and assert network requests in Playwright?

> **Observe:** `page.waitForRequest()` / `page.waitForResponse()`.
> `page.on('request', ...)` for all. Assert URL, method, headers, body.
> `response.json()` for API assertions combined with UI.

---

**Q18.** What is `page.evaluate()` and `page.evaluateHandle()`? Give a use case
for each.

> **Observe:** `evaluate()` — runs JS in browser, returns serializable value
> (string, number, plain object). `evaluateHandle()` — returns
> JSHandle/ElementHandle (live reference). Use evaluate for custom scroll, dark
> mode toggle, reading computed styles.

---

**Q19.** [Scenario] Your test clicks a button that triggers a navigation.
Sometimes the test is fast enough to assert before navigation completes. How do
you handle this reliably?

> **Observe:** `Promise.all([page.waitForNavigation(), button.click()])`. Or use
> `page.waitForURL()` after click. Modern:
> `page.waitForLoadState('networkidle')` — though `networkidle` can be slow.

---

**Q20.** How does Playwright's `expect` auto-retry differ from Selenium's
`WebDriverWait`?

> **Observe:** Playwright's `expect` retries the assertion until timeout — no
> explicit wait needed. Selenium requires explicit `ExpectedConditions`.
> Playwright's model is more ergonomic and less prone to race conditions.

---

**Q21.** Explain `playwright.config.ts` — what are the most important options
and why?

> **Observe:** `testDir`, `timeout`, `retries`, `workers`,
> `use: { baseURL, viewport, screenshot, video, trace }`, `projects`
> (cross-browser). Should mention environment-specific config via env vars.

---

**Q22.** How do you run Playwright tests against multiple browsers
simultaneously?

> **Observe:** `projects` array in config — each with `name` and
> `use: { browserName }`. CLI: `--project=chromium --project=firefox`. Each
> project can have different configs.

---

**Q23.** [Scenario] A test that deletes a record passes individually but fails
when run in the full suite. What could cause this and how do you investigate?

> **Observe:** Test order dependency, shared state, missing cleanup. Solution:
> each test creates its own data (API setup), isolated user/context, no global
> DB state assumptions.

---

**Q24.** What is the difference between `page.waitForSelector()` and
`locator.waitFor()`?

> **Observe:** `waitForSelector` is legacy selector-based. `locator.waitFor()`
> works with Playwright's Locator model, composable, and supports options like
> `{ state: 'visible' | 'hidden' | 'attached' | 'detached' }`. Prefer Locator
> API.

---

**Q25.** How do you test WebSocket communication in Playwright?

> **Observe:** `page.on('websocket', ws => ...)`. Listen to `ws.on('framesent')`
> and `ws.on('framereceived')`. Can inspect messages. Cannot mock WS easily —
> may need server-side test doubles.

---

**Q26.** Describe how you'd integrate Playwright with CI (GitHub Actions or
Jenkins). What artifacts do you publish?

> **Observe:** Install Node + browsers (`npx playwright install --with-deps`).
> Run `npx playwright test`. Publish: HTML report (`playwright-report/`), traces
> zip, screenshots/videos on failure. Cache browsers between runs.

---

**Q27.** What are `page.addInitScript()` and `context.addInitScript()`? Give a
real use case.

> **Observe:** Injects JS that runs before any page scripts. Use case: override
> `Date.now()` for time-sensitive tests, mock `window.fetch`, disable animations
> (`document.querySelector('*').style.animationDuration = '0s'`).

---

**Q28.** [Scenario] You need to automate a multi-step checkout flow with 3 users
simultaneously (concurrent). Design the test.

> **Observe:** Three `BrowserContext` objects in one test, run steps in
> `Promise.all()`. Each context has own session. Can share one browser instance.
> Test structure: setup → concurrent actions → assertions per context.

---

**Q29.** How does Playwright handle popups, new tabs, and dialogs?

> **Observe:** New tab: `page.waitForEvent('popup')`. Dialogs:
> `page.on('dialog', d => d.accept())` — register BEFORE action that triggers.
> Alert/confirm/prompt handling. `window.open` triggers popup event.

---

**Q30.** Explain `locator.filter()` and `locator.nth()`. When would you use
each?

> **Observe:** `.filter({ hasText: 'Submit' })` — narrows locator matching
> elements with text. `.nth(0)` — picks by index. Prefer `.filter()` over
> `.nth()` — index is fragile; text/attribute filtering is semantic.

---

**Q31.** What is Playwright Component Testing? How is it different from E2E
testing?

> **Observe:** Tests individual React/Vue/Svelte components in isolation,
> mounted in real browser. No full page load or backend. Uses
> `@playwright/experimental-ct-react`. Faster than E2E, more reliable than unit
> tests for UI behavior.

---

**Q32.** [Scenario] An element is visually present on screen but
`expect(locator).toBeVisible()` fails. What are the possible causes?

> **Observe:** Element has `opacity: 0`, `visibility: hidden`,
> `pointer-events: none`, is inside a `display: contents` parent, clipped by
> overflow, behind another element. Playwright checks visibility recursively up
> the DOM tree.

---

**Q33.** How do you parametrize Playwright tests? Show a TypeScript example.

> **Observe:**

```typescript
const browsers = ['chromium', 'firefox', 'webkit'];
for (const browserName of browsers) {
  test(`login on ${browserName}`, async ({ browser }) => { ... });
}
// OR using test.describe + test.use per project
```

Also: data-driven with `test.each` workaround using a loop.

---

**Q34.** What is `page.clock` in Playwright? When was it introduced and what
problem does it solve?

> **Observe:** Introduced in Playwright 1.45. Allows controlling browser clock —
> `page.clock.setFixedTime()`, `page.clock.install()`, `page.clock.tick()`.
> Replaces `addInitScript` hacks for date mocking. Essential for time-dependent
> UI features.

---

**Q35.** [Scenario] You need to validate a PDF download. The test must confirm
content, not just file existence. How?

> **Observe:** Intercept download event, save to temp path, use Node.js `fs` to
> read, pass to a PDF parser (pdf-parse). Or: open PDF URL in page context and
> parse rendered text via `page.textContent()`.

---

**Q36.** How do you implement visual regression testing with Playwright?

> **Observe:** `expect(page).toHaveScreenshot('name.png')`. First run creates
> baseline. Subsequent runs diff against baseline. `--update-snapshots` to
> refresh. Configure `threshold` for pixel tolerance. Store snapshots in VCS.

---

**Q37.** Explain `request` fixture in Playwright API testing. How does it differ
from `page.request`?

> **Observe:** `request` fixture is a standalone `APIRequestContext` — no
> browser needed. `page.request` shares browser context (cookies, auth).
> `request` fixture: cleaner for pure API tests. Both support
> `get/post/put/delete`.

---

**Q38.** [Scenario] Your Playwright suite takes 45 minutes to run. You need to
cut it to under 15 minutes. What's your strategy?

> **Observe:** Increase workers, split into shards (`--shard=1/4`), move
> API-setup heavy work to `globalSetup`, skip redundant cross-browser runs on
> PRs (full run nightly), eliminate sleep() calls, reuse auth state, parallelize
> test files.

---

**Q39.** What is `test.step()` in Playwright? How does it improve debuggability?

> **Observe:** Groups actions under a named step in the trace viewer and HTML
> report. Makes large tests navigable. Appears as collapsible sections in trace.
> Best practice for multi-step business flows.

---

**Q40.** [Scenario] A third-party payment widget loads in an iframe from
`pay.stripe.com`. You cannot pierce it due to cross-origin restrictions. How do
you test the checkout flow?

> **Observe:** Stubs/mocks the payment API route
> (`page.route('**/pay.stripe.com/**', ...)`), tests the app's success/failure
> handling. For true Stripe testing: use Stripe's test mode with test card
> numbers. Or use a test-dedicated sandbox environment.

## Section 2B: Playwright Code Review — Find the Bugs

> Present each snippet to the candidate. Ask: _"Review this test. What's wrong?
> How would you fix it?"_

### Code Review 1: Flaky Login Test

```typescript
test("user can login", async ({ page }) => {
  await page.goto("http://localhost:3000/login");
  await page.click("#email");
  await page.type("#email", "admin@test.com");
  await page.click("#password");
  await page.type("#password", "secret123");
  await page.click("button");
  await page.waitForTimeout(3000); // wait for dashboard to load
  const welcome = await page.textContent(".welcome-msg");
  expect(welcome).toBe("Welcome, Admin");
});
```

**Issues to Identify:**

1. `page.type()` is deprecated — should use `page.fill()`
2. `page.click('button')` is ambiguous — no context, could match any button
3. `page.waitForTimeout(3000)` — hardcoded sleep, root cause of flakiness;
   should use `page.waitForURL()` or `expect(locator).toBeVisible()`
4. No `baseURL` — hardcoded localhost won't work in CI
5. `await page.textContent()` then `expect()` — should use
   `await expect(page.locator('.welcome-msg')).toHaveText('Welcome, Admin')`
   (auto-waits + retries)

### Code Review 2: Data-Leaking Parallel Tests

```typescript
let productId: string;

test.describe("Product CRUD", () => {
  test("create product", async ({ page }) => {
    await page.goto("/products/new");
    await page.fill("#name", "Widget");
    await page.click("button[type=submit]");
    const url = page.url();
    productId = url.split("/").pop()!;
  });

  test("delete product", async ({ page }) => {
    await page.goto(`/products/${productId}`);
    await page.click(".delete-btn");
    await expect(page.locator(".success-toast")).toBeVisible();
  });
});
```

**Issues to Identify:**

1. `let productId` is shared mutable state — if run in parallel, second test
   gets wrong/stale value
2. Test dependency — `delete` depends on `create` running first; Playwright
   doesn't guarantee order in parallel mode
3. No cleanup — if `delete` test fails, product remains in DB; next run creates
   duplicates
4. `url.split('/').pop()!` — fragile ID extraction; better to use network
   interception to capture API response ID
5. Tests should be independent: create product in `test.beforeEach` via API, not
   through UI

### Code Review 3: Race Condition in Multi-Step Flow

```typescript
test("checkout flow", async ({ page }) => {
  await page.goto("/cart");
  await page.click("#checkout-btn");

  // Wait for payment iframe
  const frame = page.frame({ name: "payment-frame" });
  await frame!.fill("#card-number", "4242424242424242");
  await frame!.fill("#expiry", "12/26");
  await frame!.fill("#cvv", "123");

  await page.click("#pay-now");
  await page.waitForNavigation();

  expect(page.url()).toContain("/order-confirmation");
});
```

**Issues to Identify:**

1. `page.frame()` is called immediately after `click('#checkout-btn')` — iframe
   may not have loaded yet; need to `waitFor` the frame or use
   `page.frameLocator()` with built-in waiting
2. `frame!` null assertion — unsafe; should check frame exists and throw a
   meaningful error
3. `page.waitForNavigation()` called AFTER `page.click('#pay-now')` — potential
   race condition; navigation can complete before `waitForNavigation()` is
   registered. Should use
   `Promise.all([page.waitForNavigation(), page.click('#pay-now')])`
4. `expect(page.url())` — plain `expect`, no retry. Should be
   `await expect(page).toHaveURL(/order-confirmation/)`
5. No timeout configuration — default 30s may be too short/long for payment
   processing; should set explicit timeout for payment steps

## Section 2C: Tricky Playwright Config Questions (15 — Medium to Very Difficult)

> **Evaluate:** Depth of understanding of `playwright.config.ts` and the
> runner's execution model. These questions go beyond "what does this option
> do" — they probe trade-offs, precedence rules, and failure modes that only
> surface in real-world projects. Strong candidates should be able to explain
> *why* a setting behaves the way it does, not just recite the docs.

### What to Observe

- Knows precedence: CLI flag > `test.use()` > project `use` > top-level `use`.
- Distinguishes `timeout`, `expect.timeout`, `actionTimeout`, `navigationTimeout`,
  and `globalTimeout`.
- Understands `projects` vs `fullyParallel` vs `workers` vs `test.describe.configure`.
- Can explain `globalSetup`/`globalTeardown` lifecycle vs fixtures.
- Knows the cost of `trace: 'on'` vs `'retain-on-failure'` vs `'on-first-retry'`.

---

**Q1.** [Medium] In `playwright.config.ts`, you set `timeout: 30000` at the top
level, `timeout: 60000` inside a `project`, and a specific test calls
`test.setTimeout(10000)`. Which value wins for that test, and why?

> **Observe:** Precedence: `test.setTimeout()` (in-test) > project-level > top-level.
> Answer: **10 seconds** wins. Candidate should explain that `test.setTimeout`
> is dynamic and applied at runtime. Bonus: they note `test.slow()` triples the
> timeout instead.

---

**Q2.** [Medium] What's the difference between the `timeout`, `expect.timeout`,
and `use.actionTimeout` options? Give a scenario where each matters
independently.

> **Observe:**
>
> - `timeout` — whole-test timeout (default 30s).
> - `expect.timeout` — per-assertion auto-retry budget (default 5s).
> - `use.actionTimeout` — single action timeout for `click`, `fill`, etc.
>   (default: no limit, inherits test timeout).
>
> Scenario: a test that legitimately runs 45s of API setup needs
> `timeout: 60000`, but should still fail fast on a single 5s click —
> `actionTimeout: 5000`. `expect.timeout` is independent of both.

---

**Q3.** [Medium] You configure `fullyParallel: true` but one of your test files
has `test.describe.configure({ mode: 'serial' })`. What's the actual execution
behavior, and what happens if a test in that describe block fails?

> **Observe:** Files run in parallel across workers; the `serial` describe
> block runs its tests sequentially *within one worker*. **Critical detail:**
> if any test in a `serial` block fails, all subsequent tests in that block
> are **skipped**, not just failed. Candidate should also know `mode: 'default'`
> vs `'parallel'` vs `'serial'`.

---

**Q4.** [Hard] You have `retries: 2` set globally, but you want one specific
flaky test to retry 5 times without affecting others. How do you configure this?

> **Observe:** `test.describe.configure({ retries: 5 })` inside the describe,
> OR a separate `project` in config with a tag filter and `retries: 5`, OR
> `test.info().retry` to do nothing useful (red herring — you can't increase
> retries from inside a test). Best answer: project + grep tag, or describe-level
> configure.

---

**Q5.** [Hard] In `projects`, you define a `setup` project that produces
`storageState.json`, and a `chromium` project that depends on it. The setup
runs but `chromium` tests still see "not authenticated" errors. What are the
top 3 likely misconfigurations?

> **Observe:**
>
> 1. Missing `dependencies: ['setup']` on the chromium project.
> 2. `storageState` path in chromium project doesn't match the path the setup
>    wrote to (relative vs absolute, or per-worker `STORAGE_STATE` not threaded
>    through).
> 3. Setup project's `testMatch` doesn't actually match the setup file, so it
>    silently runs no tests but reports green.
>
> Bonus: `globalSetup` runs *before* projects and can't depend on a project;
> using a setup project is the modern pattern.

---

**Q6.** [Hard] What is the difference between `globalSetup` and a `setup`
project? When would you choose one over the other?

> **Observe:**
>
> - `globalSetup` — single function, runs once before all tests, can't use
>   fixtures, can't emit traces, hard to debug.
> - **Setup project** — a real Playwright test file, has full fixture support,
>   traces, reporters, and can have its own retries.
>
> Choose `globalSetup` for: env validation, one-time DB seed via raw SQL.
> Choose setup project for: anything involving the browser, auth flows,
> anything you want to debug with the trace viewer.

---

**Q7.** [Hard] You set `trace: 'on-first-retry'` and `retries: 0`. A test
fails. Why is there no trace, and what's the fix?

> **Observe:** `on-first-retry` only emits a trace on the *first retry attempt*.
> With `retries: 0` there is no retry, so no trace. Fixes:
>
> - Change to `trace: 'retain-on-failure'` (keeps trace if test fails, regardless
>   of retries).
> - Or set `retries: 1` so the first retry produces the trace.
>
> Red flag: candidate confuses `'on'` (always emits, expensive) with
> `'retain-on-failure'` (always emits, but discards on success).

---

**Q8.** [Hard] You define `use: { baseURL: process.env.BASE_URL }` at the top
level and `use: { baseURL: 'https://staging.example.com' }` inside a project.
At runtime, the project's tests still hit production. Diagnose.

> **Observe:** Most likely: `BASE_URL` env var is *also* set (e.g., from CI)
> and... wait, that's not the issue — project `use` overrides top-level `use`.
> Real cause: candidate is using `process.env.BASE_URL` inside a `test.use()`
> call that runs *after* import, but reading `process.env` at module load
> with a stale value. **Actual common bug:** `--config` is pointing at the
> wrong config file, OR there's a `playwright.config.js` shadowing the `.ts`
> one. Candidate should mention running `npx playwright test --list` to see
> resolved config.

---

**Q9.** [Hard] What does `expect.configure({ timeout: 10000 })` do that
`expect.timeout` in config does not?

> **Observe:** `expect.configure()` returns a new `expect` instance with
> overridden options — useful for assertions that need a *different* timeout
> than the default (e.g., waiting for a long-running async UI). `expect.timeout`
> in config sets the global default. Scoped override at call site:
> `const expectSlow = expect.configure({ timeout: 30000 }); await expectSlow(locator).toBeVisible();`.

---

**Q10.** [Hard] `workers: '50%'` — what does this actually compute to on a
16-core CI machine, and what's the failure mode if the worker count is too
high?

> **Observe:** `'50%'` = `Math.floor(os.cpus().length * 0.5)` = **8 workers**
> on a 16-core machine. Failure modes when over-provisioned: CPU contention
> causes timeouts (looks like flakiness), browsers OOM in containers without
> shm size tuning, network port exhaustion if each worker spins up a dev server.
> CI tip: set `workers: process.env.CI ? 4 : undefined` to cap CI but use
> all cores locally.

---

**Q11.** [Hard] Explain the difference between `testIgnore`, `testMatch`, and
`grep` / `grepInvert`. If all four are set, what's the resolution order?

> **Observe:**
>
> - `testMatch` / `testIgnore` — **file-level** filters, evaluated at discovery
>   time.
> - `grep` / `grepInvert` — **test-name** filters, evaluated after discovery.
>
> Order: discovery applies `testMatch` then `testIgnore`; runtime applies
> `grep` then `grepInvert`. A file ignored by `testIgnore` is never parsed,
> so its `grep` matches don't even fire. Candidate should know `--grep` CLI
> flag overrides config `grep`.

---

**Q12.** [Very Hard] You write a custom reporter and add it via
`reporter: [['list'], ['./my-reporter.ts']]`. It works locally but fails in
CI with "Cannot find module './my-reporter.ts'". Why?

> **Observe:** CI runs the *compiled* JS, not TS, OR the working directory
> is different so the relative path doesn't resolve. Fixes:
>
> - Use an absolute path via `require.resolve()`.
> - Publish the reporter as an installed package.
> - Ensure `ts-node` / Playwright's TS loader is available in CI (Playwright
>   does compile TS configs, but some older versions don't compile reporter
>   files the same way).
>
> Bonus: candidate mentions reporter API stability — custom reporters can break
> across Playwright minor versions.

---

**Q13.** [Very Hard] In a monorepo, you have two `playwright.config.ts` files —
one in `apps/web/` and one in `apps/admin/`. You want a single CI job to run
both suites with merged HTML reports. How do you architect this?

> **Observe:**
>
> - Option A: Run each suite separately with
>   `PLAYWRIGHT_BLOB_REPORT_DIR=blob-1` and `blob-2`, then
>   `npx playwright merge-reports --reporter=html ./blob-*` to produce a
>   single HTML report.
> - Option B: Single config with two `projects`, each with its own `testDir`
>   and `use.baseURL`. Loses per-app config isolation.
>
> Strong candidates know the `blob` reporter + `merge-reports` workflow,
> introduced specifically for sharded/multi-suite CI.

---

**Q14.** [Very Hard] You set `forbidOnly: !!process.env.CI` and a developer
pushes a PR with `test.only(...)`. The CI fails — but they argue the test
"works locally." Explain what `forbidOnly` actually does and why the local
behavior differs.

> **Observe:** `forbidOnly: true` makes the test runner **exit with an error
> at discovery time** if any `test.only()` / `describe.only()` is found.
> Locally, the dev's `CI` env var is unset, so `forbidOnly` is `false` and
> the test runs (and only that test runs, hiding suite-wide failures).
> Lesson: `forbidOnly` is a guard against accidentally committing focused
> tests. Bonus: candidate suggests `husky` pre-commit hook running
> `playwright test --list` to catch it earlier.

---

**Q15.** [Very Hard] You have `globalTimeout: 600000` (10 min) and 200 tests
with `timeout: 30000` (30s each), `workers: 4`. In theory the suite should
finish in (200 × 30s) / 4 = 1500s = 25min — well over `globalTimeout`. But
the suite consistently passes in 6 minutes. How is that possible, and what
would cause `globalTimeout` to actually trigger?

> **Observe:** `timeout: 30000` is the **maximum** per test, not actual runtime.
> Most tests finish in `<1s`. `globalTimeout` is wall-clock for the **entire
> run**, not the sum of per-test budgets. It triggers when:
>
> - A test hangs and the test-level `timeout` doesn't fire (rare — usually
>   a misconfigured fixture teardown blocks indefinitely, or a `beforeAll`
>   hook hangs without its own timeout).
> - `globalSetup` itself hangs (it has no `timeout` option unless you wrap
>   it).
> - Worker process crashes and the runner waits for it.
>
> Strong candidates note that `globalTimeout` is a safety net for CI, not
> a budget — use it to bound the worst case, not to estimate runtime.

**JS-Q7.** What is `this` in JavaScript? How does arrow function change `this`

> **Observe:** `this` is dynamic — depends on call site. Arrow functions capture

**JS-Q8.** Explain `Promise.all()` vs `Promise.allSettled()` vs

**JS-Q9.** What is the difference between deep copy and shallow copy? How do you

**JS-Q10.** What is a `WeakMap` and when would you use it vs `Map`?

> **Observe:** `WeakMap` keys must be objects, holds weak references — keys are

> key type.

### What to Observe

### Cross Questions

**Q1.** Walk me through the HTTP status code families and give one concrete
example you'd assert in an API test for each. When would a 401 vs 403 vs 404 be
the correct response for an unauthorized request to a resource that exists?

> **Observe:**
>
> - **1xx informational** (rare in tests — `100 Continue`, `101 Switching
>   Protocols` for WebSocket upgrade).
> - **2xx success:** `200 OK` (GET/PUT), `201 Created` (POST with `Location`
>   header), `202 Accepted` (async job queued), `204 No Content` (DELETE,
>   PUT with empty body). Assert `Location` on 201; assert empty body on 204.
> - **3xx redirection:** `301` permanent, `302/307` temporary, `304 Not
>   Modified` (cache validation with `If-None-Match`/`ETag`).
> - **4xx client error:** `400` malformed request, `401` unauthenticated
>   (missing/invalid credentials), `403` authenticated but not authorized,
>   `404` resource not found, `405` method not allowed, `409` conflict
>   (duplicate), `410` gone (deprecated endpoint), `415` unsupported media
>   type, `422` semantic validation failure, `429` rate limited.
> - **5xx server error:** `500` generic, `502` bad gateway, `503` service
>   unavailable (retry with backoff), `504` gateway timeout.
>
> **401 vs 403 vs 404 for an unauthorized request:**
>
> - `401` — no credentials or invalid credentials. The server doesn't know who
>   the caller is.
> - `403` — credentials are valid, but the user lacks permission to access
>   that resource.
> - `404` — sometimes returned **intentionally instead of 403** to avoid
>   leaking the existence of a resource the user can't see (common in
>   multi-tenant systems). Candidate should mention this security trade-off.
>
> **Red flag:** confuses `400` with `422`, doesn't know `409`/`429`, or
> insists `200 + { success: false }` is acceptable API design.

### 12.1 — Two Sum (Return true/false)

**Problem:** Given an array of integers and a target sum, return `true` if any
two numbers add up to the target.

```typescript
function twoSum(nums: number[], target: number): boolean {
  const seen = new Set<number>();
  for (const num of nums) {
    if (seen.has(target - num)) return true;
    seen.add(num);
  }
  return false;
}
// Tests:
console.log(twoSum([2, 7, 11, 15], 9)); // true (2+7)
console.log(twoSum([3, 5, 8], 20)); // false
console.log(twoSum([], 5)); // false
console.log(twoSum([5], 10)); // false (same element twice)
```

> **Observe:** O(n) Set solution vs O(n²) brute force. Edge cases: empty array,
> single element, negative numbers, duplicates.

### 12.2 — Anagram Check

**Problem:** Return `true` if two strings are anagrams of each other.

```typescript
function isAnagram(s: string, t: string): boolean {
  if (s.length !== t.length) return false;
  const freq = new Map<string, number>();
  for (const ch of s) freq.set(ch, (freq.get(ch) ?? 0) + 1);
  for (const ch of t) {
    const count = freq.get(ch);
    if (!count) return false;
    freq.set(ch, count - 1);
  }
  return true;
}
// Tests:
console.log(isAnagram("anagram", "nagaram")); // true
console.log(isAnagram("rat", "car")); // false
console.log(isAnagram("a", "a")); // true
console.log(isAnagram("", "")); // true
```

> **Observe:** Map-based O(n) vs sort-based O(n log n). Handling case
> sensitivity (ask: should `Listen` == `Silent`?). Unicode edge cases.

non-zero elements. In-place.

```typescript
function moveZeroes(nums: number[]): number[] {
  let insertPos = 0;
  for (const num of nums) {
    if (num !== 0) nums[insertPos++] = num;
  }
  while (insertPos < nums.length) nums[insertPos++] = 0;
  return nums;
}
// Tests:
console.log(moveZeroes([0, 1, 0, 3, 12])); // [1, 3, 12, 0, 0]
console.log(moveZeroes([0, 0, 1])); // [1, 0, 0]
console.log(moveZeroes([1, 2, 3])); // [1, 2, 3] (no zeros)
console.log(moveZeroes([0])); // [0]
```

> **Observe:** Two-pointer in-place. O(n) time, O(1) space. Maintaining order of
> non-zeros.

### 12.4 — FizzBuzz (with a twist)

**Problem:** For numbers 1–N, print "Fizz" for multiples of 3, "Buzz" for 5,
"FizzBuzz" for both. **Return an array.** Also handle: what if 3 and 5 are
configurable?

```typescript
function fizzBuzz(n: number, fizz = 3, buzz = 5): string[] {
  return Array.from({ length: n }, (_, i) => {
    const num = i + 1;
    if (num % fizz === 0 && num % buzz === 0) return "FizzBuzz";
    if (num % fizz === 0) return "Fizz";
    if (num % buzz === 0) return "Buzz";
    return String(num);
  });
}
```

> **Observe:** Configurable parameters. Array.from vs loop. Return type. Edge:
> n=0.

### 12.6 — Find the Duplicate in Array

**Problem:** Array of n+1 integers, each between 1 and n. Find the one
duplicate. O(1) space.

```typescript
function findDuplicate(nums: number[]): number {
  let slow = nums[0];
  let fast = nums[nums[0]];
  while (slow !== fast) {
    slow = nums[slow];
    fast = nums[nums[fast]];
  }
  slow = 0;
  while (slow !== fast) {
    slow = nums[slow];
    fast = nums[fast];
  }
  return slow;
}
// Alternative O(n) space but simpler:
function findDuplicateSimple(nums: number[]): number {
  const seen = new Set<number>();
  for (const n of nums) {
    if (seen.has(n)) return n;
    seen.add(n);
  }
  return -1;
}
```

> **Observe:** Floyd's cycle detection for O(1) space (advanced). Accept Set
> approach — observe if they can reason about the O(1) approach conceptually.

### 12.7 — Flatten Nested Array

**Problem:** Flatten an arbitrarily nested array. `[1, [2, [3, [4]]]]` →
`[1, 2, 3, 4]`

```typescript
function flatten(arr: any[]): number[] {
  return arr.reduce(
    (acc, val) =>
      Array.isArray(val) ? acc.concat(flatten(val)) : acc.concat(val),
    []
  );
}
// Modern:
function flattenModern(arr: any[]): number[] {
  return arr.flat(Infinity) as number[];
}
// Tests:
console.log(flatten([1, [2, [3, [4]]]])); // [1, 2, 3, 4]
console.log(flatten([1, 2, 3])); // [1, 2, 3]
console.log(flatten([])); // []
```

> **Observe:** Recursive reduce vs `Array.flat(Infinity)`. TypeScript: `any[]`
> typing challenge. Stack overflow on very deep nesting — iterative solution.

### 12.8 — Count Character Frequency

**Problem:** Given a string, return an object with character frequency, sorted
by frequency descending.

```typescript
function charFrequency(s: string): [string, number][] {
  const freq = new Map<string, number>();
  for (const ch of s) freq.set(ch, (freq.get(ch) ?? 0) + 1);
  return [...freq.entries()].sort((a, b) => b[1] - a[1]);
}
// Tests:
console.log(charFrequency("aabbccc")); // [['c',3],['a',2],['b',2]]
console.log(charFrequency("")); // []
```

> **Observe:** Map usage. Sorting by value. TypeScript destructuring. Stable
> sort behavior.

**P-Q16.** [Scenario] You need to retry an async function up to 3 times with
exponential backoff. Write the utility in TypeScript.

```typescript
async function withRetry<T>(
  fn: () => Promise<T>,
  maxAttempts: number = 3,
  baseDelay: number = 1000
): Promise<T> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === maxAttempts) throw err;
      await new Promise((r) => setTimeout(r, baseDelay * 2 ** (attempt - 1)));
    }
  }
  throw new Error("Unreachable");
}
```
