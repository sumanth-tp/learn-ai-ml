**In one line.** Fine-tuning learns exactly what the data shows it, so the work is in the data: the text must be rendered the way the model expects, the loss must fall on the answer and not the question, and the validation set must not be a disguised copy of the training set.

:::note Not from a lecture
This chapter is written for this site from the Hugging Face TRL and Transformers documentation and the SmolLM2 model and dataset cards listed under Further reading. All numbers come from the code in the chapter. The ticket data is synthetic, generated by the code, and exists to show mechanisms, not to benchmark anything.
:::

## The idea in plain words

A language model reads a stream of tokens. It has no idea what a "conversation" is until someone writes the conversation out as tokens, with markers that say where a message starts, who is speaking and where the message ends. Those markers are the **chat template**. A model fine-tuned with the wrong markers learns a format its tokenizer was never built for, and a model served with different markers from the ones it trained on behaves strangely. The template is part of the model, as much as its weights.

Once the text is rendered, the second question is **what to learn from it**. In a conversation, only the assistant's reply is the behaviour you want. The user's ticket and the system instruction are context. If the loss is computed on every token, the model spends its capacity learning to predict customer messages. **Loss masking** sets the label of every context token to a value the loss ignores, so only the answer trains.

Then come the quieter problems, which decide whether the number you report afterwards means anything: duplicates that count one example many times, near-duplicates that leak across the train and validation sets, labels that contradict each other, and padding that makes training slower than it needs to be.

Everything below uses the running example from the previous chapter, the support-ticket router that must answer in strict JSON such as `{"queue": "billing"}`, and the tokenizer of the model we fine-tune in the next chapter, `SmolLM2-135M-Instruct`.

## How it works

### Data shapes

TRL's documentation names a handful of dataset types, and which one you use decides how the trainer builds its loss mask.

| Type | Columns | Used by |
| --- | --- | --- |
| Language modelling | `text`, or `messages` for chat | SFT |
| Prompt-completion | `prompt`, `completion` | SFT, loss on the completion only by default |
| Preference | `prompt`, `chosen`, `rejected` | DPO and similar |
| Unpaired preference | `prompt`, `completion`, `label` | KTO |
| Prompt-only | `prompt` | online and RL methods such as GRPO |

Each can be **standard** (plain strings) or **conversational** (lists of role and content messages). With conversational data the trainer applies the tokenizer's chat template for you. For SFT, prompt-completion is the most convenient shape, because the trainer then computes the loss on the completion by default. Block 1 builds all three shapes from one ticket.

### The template belongs to the model

The Transformers documentation states the central fact plainly: every causal model just continues a token sequence, and a chat model is one trained on sequences with a particular layout. Different models use different layouts, even when fine-tuned from the same base. Its own examples show one Mistral model using `[INST]` markers and a Zephyr model using `<|user|>` and `<|assistant|>`, and it warns that with the wrong control tokens the model's quality is much worse.

SmolLM2 uses a ChatML-style layout. Block 1 prints the rendered text of one conversation and surfaces three details that bite in practice.

1. **A system prompt appears even when you did not write one.** The template inserts "You are a helpful AI assistant named SmolLM, trained by Hugging Face" whenever the first message is not a system message. It is 11 tokens longer than a short system prompt of our own (52 tokens against 41 for the first ticket), it is added to every example, and it is text the model sees at training time that your serving code might forget to send.
2. **The end-of-turn marker is a real token.** `<|im_end|>` is both the end-of-sequence token and, in this tokenizer, the padding token. Training must teach the model to emit it, or generation never stops. Because padding and end-of-sequence share one id, masking padding by token id would also mask the end marker.
3. **Another model's layout is not a special token here.** Writing the Zephyr-style `<|user|>` into SmolLM2's tokenizer yields five ordinary tokens, not one marker. The model never saw that spelling.

### Loss masking

Block 2 builds the mask the plain way. Render the conversation once with `add_generation_prompt=True` and without the answer, to find where the answer begins. Render the full conversation. Check that the first is a prefix of the second (if it is not, the tokenizer merged across the boundary and the split is wrong). Then set every label before the boundary to the ignore value, which is -100.

The result for the first ticket is 52 tokens with 8 carrying loss. The eight are the JSON, the `<|im_end|>` marker and the newline the template puts after it. Block 2 then builds the same dataset in prompt-completion form, lets `SFTTrainer` prepare it, and checks that TRL's labels are identical to ours for all four examples.

There is a second route that many tutorials show, `assistant_only_loss=True`, and it fails here for a reason worth knowing. It needs a chat template that wraps assistant text in `generation` markers so that the tokenizer can return an assistant mask. SmolLM2's stock template has none. Block 3 shows the Transformers warning and a mask of zero tokens, shows TRL refusing the option with an error that asks you to modify the template, and then patches the template, checks that it still renders identical text, and gets a mask of the same 8 answer tokens minus the trailing newline. The practical lesson: with a model whose template lacks those markers, use prompt-completion data and you get completion-only loss with no template surgery.

:::note
In block 2 the loss over every token is 4.5594 and over the 8 answer tokens 4.7013. The two averages cover different positions, so they differ, and which is larger depends on the example: the lab below shows the billing ticket the other way round, 4.2921 over every token against 4.1928 over the answer. What does not change is the point that the average over everything is dominated by tokens you are not trying to teach, and the effect grows as prompts get longer.
:::

### Packing

Training examples have different lengths, and a batch is a rectangle. Padding fills the short rows, and padded positions cost compute and teach nothing. Block 4 uses 48 synthetic tickets of 48 to 148 tokens and compares three ways of building rows of 512 positions.

- Padding every example to 512: 14.5 percent of computed positions are real tokens.
- Padding to the longest example in each batch of 8: 56.5 percent.
- **Packing**, placing several examples end to end in one row with a first-fit-decreasing rule: 87.2 percent, in 8 blocks.

TRL exposes this as `packing=True` with a `packing_strategy` of `bfd` (best-fit decreasing, truncating overflow), `bfd_split` or `wrapped`. The documentation also notes that the bfd strategy enables padding-free training. Packing has a cost: attention must not cross from one example into the next, which is why a library has to do it rather than a string concatenation, and loss masks must travel with each example.

### Cleaning

Block 5 builds 105 raw rows from templates and then injects defects, as real exports have them: empty tickets, a label outside the schema, an overlong ticket, case and whitespace variants of the same text, and one text with two labels. A pipeline of simple, separately counted steps takes it from 105 to 71.

- **Drop invalid rows** (empty, outside the label schema, too long): 105 to 98.
- **Exact duplicates after normalising** case and whitespace: 98 to 84.
- **Conflicting labels**: if the same text carries two labels, drop it rather than pick one: 84 to 83.
- **Near-duplicates** by three-word shingles and Jaccard similarity of 0.8 or more: 83 to 71. The generator only varies a greeting and a sign-off around the same sentence, so tickets differ in a few words, and near-duplicate removal is what catches them. Real data is not that extreme, but customer-written text repeats in the same way.

Count what each step removes and keep the counts. A step that suddenly removes half the data is a bug report about the data source.

### Splitting and contamination

A random split puts a paraphrase of a training ticket into validation, and the validation score then measures memorisation. Block 5 shows it. After a **grouped split**, where whole underlying issues (not rows) go to one side, no validation row shares more than half its four-word sequences with training. After a random split of the same rows, 21 of 26 validation rows do. Same data, same size, and the second validation set would flatter the model.

The same logic applies to any external test set: compute the overlap of its n-grams with the training data before you train, and remove or report anything that overlaps. This is **contamination checking**, and it is cheap compared with explaining an inflated result later.

## A real system that works this way

**SmolLM2-135M-Instruct** is the model fine-tuned throughout this series, and its documentation shows the same data choices. The model card says it was post-trained in two stages, supervised fine-tuning and then DPO on UltraFeedback. The dataset card for **smol-smoltalk**, the supervised set, describes it as a subset of SmolTalk adapted for models under one billion parameters, with reduced length and fewer task-specific examples, 460,000 training rows and 24,200 test rows under an Apache 2.0 licence. The dataset was shaped for the model size: the data was made shorter and simpler because the model is small. That is the same decision as block 4, taken at larger scale.

**The LIMA paper** is the clearest argument for spending effort on data quality over volume: it fine-tuned a 65B model on 1,000 curated prompt and response pairs and reported that it produced high-quality output, supporting the claim that almost all knowledge comes from pre-training and a small amount of instruction data is enough to teach format and style.

## Code you can run

Five blocks. Each loads the SmolLM2 tokenizer (about a second once cached); block 2 also loads the model once. The whole set runs in about a minute on a laptop CPU.

### 1. The same ticket in three dataset shapes, and the real template

```python
import json
import os

os.environ["HF_HUB_DISABLE_PROGRESS_BARS"] = "1"
from transformers import AutoTokenizer

name = "HuggingFaceTB/SmolLM2-135M-Instruct"
tokenizer = AutoTokenizer.from_pretrained(name)

ticket = "Hi team, I forgot my password and the reset email never arrives."
answer = json.dumps({"queue": "account"})

formats = {
    "language modelling": {"text": f"{ticket}\n{answer}"},
    "conversational": {"messages": [{"role": "user", "content": ticket}, {"role": "assistant", "content": answer}]},
    "prompt-completion": {
        "prompt": [{"role": "user", "content": ticket}],
        "completion": [{"role": "assistant", "content": answer}],
    },
}
for kind, example in formats.items():
    print(f"{kind:<20} columns: {sorted(example)}")

messages = formats["conversational"]["messages"]
text = tokenizer.apply_chat_template(messages, tokenize=False)
print("\nrendered by the real SmolLM2 template:")
print(text)

with_default = tokenizer.apply_chat_template(messages, tokenize=True, return_dict=True)["input_ids"]
```

### 2. A loss mask by hand, checked against TRL

```python
import json
import os

os.environ["HF_HUB_DISABLE_PROGRESS_BARS"] = "1"
import torch
from datasets import Dataset
from transformers import AutoTokenizer
from trl import SFTConfig, SFTTrainer

name = "HuggingFaceTB/SmolLM2-135M-Instruct"
tokenizer = AutoTokenizer.from_pretrained(name)

rows = [
    ("Hi team, I forgot my password and the reset email never arrives.", "account"),
    ("Hello, I was charged twice for my subscription this month. Thanks.", "billing"),
    ("The app crashes every time I open the dashboard. Please help.", "technical"),
    ("I need to change the email address on my account.", "account"),
]


def prompt_messages(ticket):
    return [{"role": "user", "content": ticket}]


def completion_messages(queue):
    return [{"role": "assistant", "content": json.dumps({"queue": queue})}]


def encode_with_mask(ticket, queue):
    prompt_ids = tokenizer.apply_chat_template(prompt_messages(ticket), add_generation_prompt=True, tokenize=True, return_dict=True)["input_ids"]
    full_ids = tokenizer.apply_chat_template(prompt_messages(ticket) + completion_messages(queue), tokenize=True, return_dict=True)["input_ids"]
    assert full_ids[: len(prompt_ids)] == prompt_ids
    labels = [-100] * len(prompt_ids) + full_ids[len(prompt_ids):]
    return full_ids, labels


ids, labels = encode_with_mask(*rows[0])
print(f"{len(ids)} tokens in total, {sum(l != -100 for l in labels)} carry loss")
for token_id, label in list(zip(ids, labels))[-12:]:
    shown = tokenizer.decode(token_id).replace("\n", "\\n")
    print(f"  {token_id:>6}  {shown:<14} {'trained' if label != -100 else 'masked'}")

for ticket, queue in rows:
    i, l = encode_with_mask(ticket, queue)
    print(f"{queue:<10} {len(i):>3} tokens, {sum(x != -100 for x in l):>2} trained ({sum(x != -100 for x in l) / len(i):.0%})")

dataset = Dataset.from_list([{"prompt": prompt_messages(t), "completion": completion_messages(q)} for t, q in rows])
trainer = SFTTrainer(
    model=name,
    args=SFTConfig(output_dir="sft-mask-check", report_to="none", max_length=128, use_cpu=True, per_device_train_batch_size=2),
    train_dataset=dataset,
    processing_class=tokenizer,
)
agree = all(
    trainer.train_dataset[k]["input_ids"] == encode_with_mask(*rows[k])[0] and trainer.train_dataset[k]["labels"] == encode_with_mask(*rows[k])[1]
    for k in range(len(rows))
)
print(f"\nour mask equals the one TRL builds for prompt-completion data: {agree}")

batch = trainer.data_collator([trainer.train_dataset[0], trainer.train_dataset[1]])
padded = (batch["attention_mask"] == 0).sum().item()
print(f"collator padded {padded} positions; their labels are all -100: {bool((batch['labels'][batch['attention_mask'] == 0] == -100).all())}")

model = trainer.model.eval()
input_ids = torch.tensor([ids])
with torch.no_grad():
    loss_all = model(input_ids=input_ids, labels=input_ids).loss.item()
    loss_masked = model(input_ids=input_ids, labels=torch.tensor([labels])).loss.item()
print(f"loss over every token {loss_all:.4f}, loss over the 8 assistant tokens only {loss_masked:.4f}")
```

```text
       1  <|im_start|>   masked
     520  ass            masked
    9531  istant         masked
     198  \n             masked
   39428  {"             trained
   16301  queue          trained
    1799  ":             trained
     476   "             trained
   12016  account        trained
   23597  "}             trained
```

### 3. Why `assistant_only_loss` fails here, and a template patch

```python
import os

os.environ["HF_HUB_DISABLE_PROGRESS_BARS"] = "1"
from transformers import AutoTokenizer

name = "HuggingFaceTB/SmolLM2-135M-Instruct"
tokenizer = AutoTokenizer.from_pretrained(name)

PATCHED = (
    "{% for message in messages %}"
    "{% if loop.first and messages[0]['role'] != 'system' %}"
    "{{ '<|im_start|>system\nYou are a helpful AI assistant named SmolLM, trained by Hugging Face<|im_end|>\n' }}"
    "{% endif %}"
    "{% if message['role'] == 'assistant' %}"
    "{{ '<|im_start|>assistant\n' }}{% generation %}{{ message['content'] + '<|im_end|>' }}{% endgeneration %}{{ '\n' }}"
    "{% else %}"
    "{{ '<|im_start|>' + message['role'] + '\n' + message['content'] + '<|im_end|>' + '\n' }}"
    "{% endif %}"
    "{% endfor %}"
    "{% if add_generation_prompt %}{{ '<|im_start|>assistant\n' }}{% endif %}"
)

messages = [
    {"role": "user", "content": "My card was charged twice."},
    {"role": "assistant", "content": '{"queue": "billing"}'},
]

stock = tokenizer.apply_chat_template(messages, return_dict=True, return_assistant_tokens_mask=True)
print(f"stock template: assistant tokens marked = {sum(stock['assistant_masks'])} of {len(stock['input_ids'])}")

patched = AutoTokenizer.from_pretrained(name)
patched.chat_template = PATCHED
same_text = tokenizer.apply_chat_template(messages, tokenize=False) == patched.apply_chat_template(messages, tokenize=False)
print(f"patched template renders identical text: {same_text}")
result = patched.apply_chat_template(messages, return_dict=True, return_assistant_tokens_mask=True)
marked = [tokenizer.decode(i) for i, m in zip(result["input_ids"], result["assistant_masks"]) if m]
print(f"patched template: assistant tokens marked = {sum(result['assistant_masks'])} of {len(result['input_ids'])}")
print("marked:", marked)
```

What it prints:

```text
stock template: assistant tokens marked = 0 of 45
patched template renders identical text: True
patched template: assistant tokens marked = 8 of 45
marked: ['{"', 'queue', '":', ' "', 'b', 'illing', '"}', '<|im_end|>']
```

The stock template marks no assistant tokens. The patched one marks 8, and a check that it renders identical text is the test that you changed only the markers. TRL's own error for the stock template, in this release (TRL 1.14.1), reads: "The chat template is not training-compatible (missing prefix-preservation or `{% generation %}` markers) and patching is not supported for this template. Please manually modify the chat template for training."

### 4. Packing

```python
import os
import random

os.environ["HF_HUB_DISABLE_PROGRESS_BARS"] = "1"
from transformers import AutoTokenizer

name = "HuggingFaceTB/SmolLM2-135M-Instruct"
tokenizer = AutoTokenizer.from_pretrained(name)

rng = random.Random(0)
stories = [
    "The app crashes every time I open the dashboard.",
    "I was charged twice for my subscription this month.",
    "I forgot my password and the reset email never arrives.",
]
queues = ["technical", "billing", "account"]
examples = []
for i in range(48):
    k = i % 3
    repeats = rng.choice([1, 1, 1, 2, 3, 6, 10])
    ticket = " ".join(stories[k] for _ in range(repeats))
    messages = [{"role": "user", "content": ticket}, {"role": "assistant", "content": '{"queue": "%s"}' % queues[k]}]
    examples.append(len(tokenizer.apply_chat_template(messages, tokenize=True, return_dict=True)["input_ids"]))

BLOCK = 512
real = sum(examples)
print(f"{len(examples)} examples, {real} real tokens, lengths from {min(examples)} to {max(examples)}")

fixed = len(examples) * BLOCK
print(f"pad every example to {BLOCK}: {fixed} positions computed, {real / fixed:.1%} useful")

order = list(range(len(examples)))
rng.shuffle(order)
batches = [order[i:i + 8] for i in range(0, len(order), 8)]
dynamic = sum(len(b) * max(examples[j] for j in b) for b in batches)
print(f"pad to the longest in each batch of 8: {dynamic} positions, {real / dynamic:.1%} useful")

bins = []
for length in sorted(examples, reverse=True):
    for b in bins:
        if sum(b) + length <= BLOCK:
            b.append(length)
            break
    else:
        bins.append([length])
packed = len(bins) * BLOCK
print(f"first-fit decreasing into {BLOCK}-token blocks: {len(bins)} blocks, {packed} positions, {real / packed:.1%} useful")
print(f"fullest block holds {max(len(b) for b in bins)} examples; emptiest block is {min(sum(b) for b in bins)} tokens full")
```

What it prints:

```text
48 examples, 3570 real tokens, lengths from 48 to 148
pad every example to 512: 24576 positions computed, 14.5% useful
pad to the longest in each batch of 8: 6320 positions, 56.5% useful
first-fit decreasing into 512-token blocks: 8 blocks, 4096 positions, 87.2% useful
fullest block holds 10 examples; emptiest block is 144 tokens full
```

### 5. Cleaning, a grouped split and a leakage check

```python
import os
import random

os.environ["HF_HUB_DISABLE_PROGRESS_BARS"] = "1"
from transformers import AutoTokenizer

name = "HuggingFaceTB/SmolLM2-135M-Instruct"
tokenizer = AutoTokenizer.from_pretrained(name)

ISSUES = {
    "billing": ["I was charged twice for my subscription this month", "my invoice shows an amount I do not recognise", "I need a refund for the annual plan I bought by mistake", "the card on file was declined but my bank says it is fine", "please send me a receipt for last month's payment", "I was billed after I cancelled"],
    "technical": ["the app crashes every time I open the dashboard", "the export button does nothing when I click it", "I get a 500 error when I upload a file", "pages take more than a minute to load", "the mobile app freezes on the login screen", "the API returns an empty list for my project"],
    "account": ["I forgot my password and the reset email never arrives", "I need to change the email address on my account", "please delete my account and all my data", "I cannot enable two-factor authentication", "my teammate needs access to our workspace", "my account was locked after too many login attempts"],
}
OPENERS = ["Hi,", "Hello,", "Hi team,", "Good morning,", "", "Hey,"]
CLOSERS = ["Thanks.", "Please help.", "Thank you in advance.", "", "This is urgent.", "Regards, Sam"]

rng = random.Random(0)
rows = []
for queue, issues in ISSUES.items():
    for k, issue in enumerate(issues):
        for _ in range(5):
            text = " ".join(p for p in [rng.choice(OPENERS), issue[0].upper() + issue[1:] + ".", rng.choice(CLOSERS)] if p)
            rows.append({"ticket": text, "queue": queue, "issue": k})

rows += [{"ticket": "   ", "queue": "billing", "issue": 0}] * 3
rows += [{"ticket": "", "queue": "account", "issue": 0}] * 2
rows += [dict(r, ticket=r["ticket"].upper()) for r in rows[:4]]
rows += [dict(r, ticket="  " + r["ticket"] + "  ") for r in rows[5:8]]
rows += [dict(rows[10], queue="technical" if rows[10]["queue"] != "technical" else "billing")]
rows += [dict(rows[20], queue="urgent")]
rows += [dict(rows[30], ticket=rows[30]["ticket"] + " " + "Please look into this. " * 40)]
rng.shuffle(rows)
print(f"raw rows: {len(rows)}")


def normal(text):
    return " ".join(text.lower().split())


def shingles(text, n=3):
    words = normal(text).split()
    return {" ".join(words[i:i + n]) for i in range(max(1, len(words) - n + 1))}


def jaccard(a, b):
    return len(a & b) / len(a | b)


steps = []
kept = [r for r in rows if r["ticket"].strip()]
steps.append(("drop empty", len(kept)))
kept = [r for r in kept if r["queue"] in ISSUES]
steps.append(("drop labels outside the schema", len(kept)))
kept = [r for r in kept if len(tokenizer(r["ticket"])["input_ids"]) <= 128]
steps.append(("drop longer than 128 tokens", len(kept)))

seen, unique = {}, []
for r in kept:
    key = normal(r["ticket"])
    if key in seen:
        continue
    seen[key] = r["queue"]
    unique.append(r)
steps.append(("drop exact duplicates after normalising", len(unique)))

by_text = {}
for r in kept:
    by_text.setdefault(normal(r["ticket"]), set()).add(r["queue"])
conflicts = {t for t, qs in by_text.items() if len(qs) > 1}
unique = [r for r in unique if normal(r["ticket"]) not in conflicts]
steps.append(("drop texts with conflicting labels", len(unique)))

near, sigs = [], []
for r in unique:
    s = shingles(r["ticket"])
    if any(jaccard(s, t) >= 0.8 for t in sigs):
        continue
    sigs.append(s)
    near.append(r)
steps.append(("drop near duplicates (3-gram Jaccard 0.8 or more)", len(near)))
for label, count in steps:
    print(f"{label:<52}{count:>5}")

held_out_issues = {(q, k) for q in ISSUES for k in (4, 5)}
train = [r for r in near if (r["queue"], r["issue"]) not in held_out_issues]
valid = [r for r in near if (r["queue"], r["issue"]) in held_out_issues]
print(f"\ngrouped split by underlying issue: {len(train)} train, {len(valid)} validation")

train_grams = set().union(*(shingles(r["ticket"], 4) for r in train))
leaks = [r for r in valid if len(shingles(r["ticket"], 4) & train_grams) / len(shingles(r["ticket"], 4)) > 0.5]
print(f"validation rows sharing more than half their 4-grams with train: {len(leaks)}")

random_valid = rng.sample(near, len(valid))
random_train = [r for r in near if r not in random_valid]
random_grams = set().union(*(shingles(r["ticket"], 4) for r in random_train))
random_leaks = [r for r in random_valid if len(shingles(r["ticket"], 4) & random_grams) / len(shingles(r["ticket"], 4)) > 0.5]
print(f"same check after a random split of the same rows: {len(random_leaks)} of {len(random_valid)}")
```

## Designing with it

1. **Open the rendered text of one training example and read it.** Most data bugs are visible there.
2. **Use the model's own template, for training and serving.** If you must change it, change the same template in both places and keep a test that renders both identically.
3. **Choose prompt-completion for SFT unless you need multi-turn masks.** It gives completion-only loss without touching the template.
4. **Check the end-of-turn token is in the labels.** Without it, generation will not stop.
5. **Split by the thing that repeats.** If tickets repeat per customer, per template or per source document, split by that, not by row.
6. **Count every cleaning step.** Keep the funnel numbers with the dataset version.
7. **Look at near-duplicates before deleting them.** A cluster of near-identical rows can be a template you want to keep one of, or a sign that the sampling is wrong.

## Where this stands in 2026

:::info Industry view
- **Templates are shipped with the model, and the tooling now checks them.** The TRL release used here refuses `assistant_only_loss=True` on a template without generation markers rather than silently training on everything. For known families the documentation says TRL patches the template automatically, and it lists bundled training templates; for other models you patch it yourself.
- **Prompt-completion is the low-friction path.** TRL's SFT documentation lists it as a first-class type, with the completion-only default.
- **Packing is a library feature, not a hand job.** TRL offers named strategies and ties one of them to padding-free training. Check what your version does at example boundaries before trusting it with multi-turn chat.
- **Contamination checking is a norm for evaluation sets.** It is cheap, and the data-leakage numbers in block 5 show how easily a random split flatters a model.
- **I could not verify** any claim about which companies use which packing or dedup method; none is made here.
:::

## Practice questions

<details>
<summary><strong>Q1.</strong> A colleague fine-tunes on prompts rendered as plain text, "Ticket: ... Answer: ...", then serves the model through its chat template. What goes wrong?</summary>

The model learned one layout and is asked to continue another. The end-of-turn and role markers it was trained to produce are not the ones the serving template expects, so replies may not stop, may repeat the prompt or may ignore the instruction. Train and serve with the same rendering, ideally the tokenizer's own template.<br /><em>Authored · applied</em>

</details>

<details>
<summary><strong>Q2.</strong> In block 2, the loss over the 8 answer tokens (4.7013) is higher than over all tokens (4.5594) for the account ticket. Is the model worse at answers?</summary>

Not necessarily. The two averages cover different positions: one includes the fixed system prompt and common English words, the other only the JSON the model has to learn. For this ticket the context is easier, so the full average is lower; for the billing ticket in the lab it is the other way round. The masked loss is the one that tracks the behaviour you are teaching, whichever way the numbers fall.<br /><em>Authored · interpretation</em>

</details>

<details>
<summary><strong>Q3.</strong> Why does masking padding by comparing token ids to the pad id damage SmolLM2 training, and what does the collator do instead?</summary>

For this tokenizer the pad token and the end-of-turn token are the same id, 2. Masking every position whose id equals the pad id would also mask the real `<|im_end|>` the model must learn to emit. The collator uses the attention mask to find padding, and block 2 shows the padded position labelled -100 while the real end marker stays in the labels.<br /><em>Authored · conceptual</em>

</details>

<details>
<summary><strong>Q4.</strong> Block 5's grouped split leaves 0 leaking validation rows and a random split leaves 21 of 26. What does this say about validation accuracy on each?</summary>

On the random split, most validation rows are close paraphrases of training rows, so a model that memorised training would score well without generalising. Validation accuracy there is optimistic. On the grouped split every validation issue is unseen, so the score reflects how the model treats new situations, which is what production will ask of it.<br /><em>Authored · interpretation</em>

</details>

<details>
<summary><strong>Q5.</strong> Packing raised useful positions from 56.5 to 87.2 percent in block 4. Name one risk that the percentage does not show.</summary>

Examples in a block must not attend to each other, and their loss masks must stay attached to the right tokens. A naive concatenation lets later examples see earlier ones and mixes contexts. Use a library implementation that handles boundaries, and test that the loss of a packed run matches an unpacked run on a small sample.<br /><em>Authored · applied</em>

</details>

<details>
<summary><strong>Q6.</strong> You find the same ticket text labelled billing in one row and technical in another. What do you do, and why not keep the majority?</summary>

First look at why: a genuinely ambiguous ticket, a labelling error, or two taxonomies merged. Dropping the text is the safe default for training, because the model gets contradictory targets for identical input. Keeping the majority hides the disagreement; a high rate of conflicts says the label definition needs fixing, and that should reach whoever owns the labels.<br /><em>Authored · applied</em>

</details>
